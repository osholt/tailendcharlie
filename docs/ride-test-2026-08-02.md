# Ride test — Sunday 2 August 2026

A real group ride with mixed Android and iOS phones. This is the only route to
three gates that cannot be reached on a desk, and it is **one pass** — if a
measurement is missed it waits for the next ride.

Priorities, in order. Anything else is opportunistic.

1. **Nearby radio matrix** (#268) — the P0 gate that holds 69 issues open.
2. **Background recording** (#205) — the product premise.
3. **Marker and pass counting** (#271) — the gate that keeps marker assistance in
   development alpha.

## Read this first: four things that will silently invalidate results

**1. Everyone must join the ride *before* mobile data goes off.** Joining needs a
connection once. A phone that tries to join with data already off will not be in
the ride at all, and the radio test will look like a radio failure.

**2. Joining by the six-digit code is fine.** An earlier version of this document
said it wasn't, repeating a claim in PLAN.md. That claim is wrong, and the code
settles it: the relay returns the ride's `inviteSecret` for a bare six-digit code
and only checks a resolve token *if one is supplied*
([service.py:532](../apps/server/src/ride_relay_server/service.py)). A rider who
types the code gets fully hardened credentials and authenticated nearby works
normally.

The resolve token still matters — it exempts the lookup from a stricter global
rate limit and stops a six-digit code being enumerated — so sharing the invite is
better practice. But it is **not** a precondition for the radio test, and nobody's
results are void for having typed a code.

**3. Wi-Fi must not be associated with a common access point.** At a café stop,
several phones joining the same guest Wi-Fi will exchange events over the local
network and look like a Nearby success. Turn Wi-Fi **off**, not just
disconnected-for-now.

**4. Android phones cannot be driven remotely.** The test-control surface is
shared Flutter code and runs on Android, but its switch lives in an iOS Settings
bundle, so there is no way to turn it on on Android yet. **Android data on Sunday
is collected by hand and by export.** Don't plan around driving them.

## Before departure — 15 minutes, at the meet point

Per phone, recorded on the sheet at the end of this document:

- Model, OS version, app build number (**Settings → About & build**)
- Battery percentage at departure, and battery health
  (iOS: Settings → Battery → Battery Health; Android: varies)
- Where the phone will live for the ride: jacket pocket, tank bag, top box, or
  mounted
- Whether another navigation app will be running in front of Tail End Charlie

Then:

1. Leader creates the ride and **shares the invite** to every rider individually.
2. Every rider joins and confirms they can see the roster with everyone on it.
3. Confirm the rider count on the leader's phone equals the number of bikes
   present. If it doesn't, stop and note it — that is #132 and worth more than
   anything else on this list.
4. Leader starts the ride.

## Assignments

Give each rider one job. Nobody needs to do anything while moving.

| Role | Who | What they do |
| --- | --- | --- |
| **Leader** | 1 rider | Creates and starts the ride, shares the invite, publishes the route. Phone mounted, screen on. |
| **TEC** | 1 rider | Last on the road. Phone mounted, screen on. |
| **Marker** | 1–2 riders | Marker duty at the named junctions below. Needs to be comfortable stopping and rejoining. |
| **Pocket rider** | 1 rider | Phone in a **jacket pocket, screen off**, for the whole ride. Does not look at it. |
| **Other-nav rider** | 1 rider | Runs their usual navigation app in front, Tail End Charlie in the background. |
| **Radio four** | 2 Android + 2 iOS | Any four riders, for the stop experiments. Can double up with the above. |

## Priority 1 — Nearby radio matrix, at a stop

**Where:** any stop of 20 minutes or more. Needs four phones and a bit of space —
about 50 m of car park is enough for the first part.

**Setup, in this order:** all four phones already in the ride (done at departure)
→ **mobile data off** → **Wi-Fi off** → Bluetooth **on** → app open, screen on.

Then work through the pairings. For each, one phone reports a hazard and you time
how long it takes to appear on the other. Reset by clearing the hazard, or just
use a different hazard type each time so nothing is deduplicated — **reports of
the same type within 75 m of each other get merged**, and a merged report looks
exactly like a delivery failure.

| # | Pairing | Delivered? | Seconds | Notes |
| --- | --- | --- | --- | --- |
| 1 | Android → Android | | | |
| 2 | iPhone → iPhone | | | |
| 3 | Android → iPhone | | | |
| 4 | iPhone → Android | | | |

Pairings 3 and 4 are the ones nothing else in this project has ever evidenced.
Both directions matter separately — the platforms advertise and discover
differently, so one working does not imply the other.

For each pairing also note what the **connectivity card** says: which medium it
claims (Bluetooth, BLE, Wi-Fi LAN), and whether it asked for any permission.

### A → B → C carry, where A and C never meet

Immediately after, same four phones, still no mobile data:

1. Rider **A** and rider **C** stand ~150 m apart, out of Bluetooth range. Confirm
   they cannot see each other's reports.
2. **A** reports a hazard while **B** stands next to them.
3. **B** walks to **C**.
4. Does the hazard reach **C**? How long after B arrives?

This is step 13 and it is the strongest single demonstration the store-and-forward
design works. It has never been run.

### Then, before riding on

**Turn mobile data and Wi-Fi back on for everyone.** Easy to forget, and the rest
of the ride is worthless without it.

## Priority 2 — Background recording, whole ride

Nothing to do beyond carrying the phone as assigned. The evidence is the recorded
trail versus the roads actually ridden.

The failure signature from the Isle of Man report is a **straight line between two
fixes** where the rider actually followed the road, and a recorded distance far
short of the real one — 0.8 miles logged over 1 hour 19 minutes.

At the end, for each of the pocket rider, the other-nav rider and one mounted
control rider, record:

| | Pocket rider | Other-nav rider | Mounted control |
| --- | --- | --- | --- |
| Distance the app recorded | | | |

| Number of visible straight-line gaps | | | |

The mounted control matters. Without it a poor result cannot be separated from
generally poor GPS on the day.

## Priority 3 — Marker and pass counting

Pick **three junctions on the route in advance** and write them here before
setting off. Aim for one of each:

- a **roundabout**
- a **staggered junction** or crossroads
- somewhere a **parallel road** runs within ~50 m, or an urban section with
  buildings close on both sides

The decisive number is **bikes that actually passed versus the count the app
showed**. Everything else in #271 is secondary to that.

If a marker session produces a suggestion that is obviously wrong, note *what*
was wrong — a junction the group rode straight through, the wrong side of a
dual carriageway, a bike counted twice.

## Opportunistic, if it costs nothing

- **Battery** (#269). Just the end-of-ride percentage against the departure
  figure already recorded, plus total ride duration. The gate is 45% over four
  hours screen-off. An Android phone with aggressive battery management is the
  most valuable single reading here, because nothing else can produce it.
- **Visor legibility** (step 21). One photograph of a mounted phone in daylight,
  through a tinted visor, in each map style. The photograph *is* the evidence;
  measured contrast ratios are not.
- **Safety-contact page** (#274). Have a non-riding friend or partner open a
  watcher link. Expect **no map, only coordinates** — that is the known missing
  operator map style. What is worth capturing is their reaction: whether a person
  who is not a rider can make any use of it.
- **Roundabout instructions** (#163). Only if the route happens through
  New Cheltenham Road, BS15 1UJ toward Chippenham — the two mini-roundabouts
  should appear as two separate second-exit instructions 42 m apart.

## After the ride

Back on Wi-Fi, with the app open and Field test control on:

- iOS phones can be read directly — roster, presence, hazards, and the
  roster/presence reconciliation — see
  [test-control-api.md](test-control-api.md).
- Android phones and everyone's ride history need exporting by hand: **Previous
  rides → the ride → export GPX / summary**.
- Send the recap image and GPX for the pocket rider and the other-nav rider.
  Those two files are the #205 evidence.

Results go in [field-test-results.md](field-test-results.md) against the pass
gates in [field-test-plan.md](field-test-plan.md). A step with no measurement is
a fail, not a blank.

## What this ride can and cannot settle

**Can:** the Nearby radio matrix including both cross-platform directions,
store-and-forward carry, background recording on real hardware in real placements,
marker and pass accuracy at real speeds, and battery on both platforms.

**Cannot:** anything needing the app driven mid-ride, since the phones are on
cellular and not reachable. Anything on Android through the test-control surface,
until it has a switch there. And the locked-screen and force-quit radio cases,
which need bench conditions rather than a moving group.
